# Android, touch controls and diagnostics

## Current status

The experimental Android APK runs the **shared C++ sandbox and MotionLab** with the engine's Vulkan renderer, bundled `AvatarSample.vrm`, two skinned glTF props, 77 BVH clips and the ImGui editor. On-screen native controls provide a floating movement stick, camera drag, and jump, attack, use, crouch and sprint; the compact upper panel opens the editor, advances clips and adjusts rendering settings. Pointers are tracked independently and cancelled on pause. Touches beginning over visible ImGui windows are reserved for ImGui; other pointers operate the game controls. The Activity is landscape-only, and the Android software keyboard is not yet integrated with ImGui text fields.

Mobile starts with NPCs and spring bones disabled; **NPCs** in the mobile panel loads the two packaged NPC models and adds the MotionLab crowd. It limits imported textures to 1024 pixels and uses smaller shadow atlases than desktop. Point-light shadows and bloom start off to reduce GPU work; turn them on in the mobile panel if desired. The mobile panel shows averaged wall-clock FPS, a paged **CLIPS** browser, and controls for hair physics and upright correction. Hair physics also affects spring-driven clothes and accessories; it is off by default on mobile and can reduce performance. Moving returns from clip playback to motion matching. The other desktop scenes and editor are available, but this is **not feature or asset parity** with the desktop configuration. The complete 77-clip library includes jump motions. If Vulkan initialization or rendering fails, the app displays a **separate Canvas synthetic-rig preview** with all 77 clips, not the 3D sandbox; its CLIPS button opens a scrollable picker. It supports Android 8 (API 26) or newer on arm64-v8a and x86_64, with Vulkan 1.3 and additional renderer capability requirements for the 3D scene; not every Android 8+ device qualifies.

The `Android sandbox` workflow builds and validates the APK, and requires a Vulkan sandbox frame on an x86_64 SwiftShader emulator. It exercises the ImGui checkbox and editor, avatar movement, clip selection, NPCs, retained settings after background/resume, and a user theme after process restart. It also exercises the Vulkan animation browser, forces the Canvas fallback, checks its 77 clips and clip picker, and backgrounds and resumes it; it uploads screenshots and a short video. These interaction/render checks are separate from the GPU-free unit tests. Download `sakuga-android-animation-preview-debug` from a successful workflow run's artifacts; GitHub may require sign-in. The APK uses an ephemeral debug key: it is **not** a Play Store build and builds from different runs may not upgrade one another. Uninstall the previous build if signing keys differ. No physical Android phone has been validated, and the emulator is not evidence of phone compatibility or performance. The Vulkan path uses FIFO presentation for display pacing instead of a fixed sleep after each frame; a slow device can still miss refresh deadlines. Neither 60 FPS nor compatibility with any particular phone is guaranteed.

To build locally, install Android SDK platform 35, build-tools 35.0.0, NDK 27.2.12479018, JDK, Python, CMake, Ninja and zip; set `ANDROID_HOME`, run `bash tools/fetch_assets.sh --motion-only` and then `bash android/build-apk.sh`. The latter requires all 77 clips in `~/.cache/lafan1` (or `SAKUGA_ANDROID_MOTION_DIR`), verifies their SHA-256 hashes, includes the verified source-mirror files and checks the signed APK. Missing or altered files fail the build. The approximately 333 MB of extracted clips and separate rig-specific per-device motion caches require significant storage, memory and first-start processing. The fallback is built on demand after Vulkan resources are released, to avoid keeping both databases in memory. LAFAN1 is by Ubisoft La Forge, licensed **CC BY-NC-ND 4.0**: non-commercial only, no sharing adapted material. See [the packaged notice and license](../assets/licenses/LAFAN1-NOTICE.txt). Review licensing before distribution. Output is in `android/output/`.

Surface recreation rebuilds Vulkan resources and restores an in-process CPU snapshot of scene and editor settings, character transforms and tuning, material parameters, and the loaded NPC crowd. A browsed clip restarts; motion transitions, spring/IK simulation history, and NPC paths are not preserved. Most state is lost if Android kills the process. Use **UI theme** in the mobile panel and **Save** in the theme window to persist a theme to app-private `files/sandbox/user/ui_theme.json` across process restarts and APK updates. App uninstall or clearing app data removes it. Rendering pauses and active touches are cancelled when the Activity pauses.

NPC model credit: Seed-san by VirtualCast, Inc.; three-vrm-girl by pixiv Inc. See the [port plan](ANDROID_PORT_PLAN.md) for licensing and remaining limitations. Linux/macOS packages remain future work.

The AI-generated files in `assets/branding/` are **concept artwork**, not screenshots or the actual in-app character. The 512px PNG is used as the Android preview launcher icon, but it is not yet wired into the Windows executable or an Android adaptive icon. The wide banner should be labelled concept art when shown to users.

## Device and performance panel

Open **Device and performance** in the main ImGui panel. It reports CPU name and logical threads when available, total and available RAM, free and total space on the app's volume, Vulkan device name and API version, device-local memory heap size, framebuffer size, FPS, averaged frame time, renderer CPU time, draw calls and triangles. A device-local heap may be shared memory and is not necessarily dedicated VRAM. Values come from the local OS or Vulkan device; unavailable values are shown as such. Storage medium is explicitly **unknown**, not guessed as HDD or SSD. No GPU time or utilization is measured. These numbers are diagnostic, not a performance rating.

The **Motion matching** panel shows current clip index and name against loaded total, frame, matcher transitions and matching/browser mode. The number is the count loaded into this session, not necessarily 77.

## Reproduce the GPU-free animation test and debug visualization

The LAFAN1 data must be fetched separately, respecting its license (`tools/fetch_assets.sh --motion-only`). The full-library test skips if insufficient clips are installed. With the full set available:

```sh
cmake -S tests -B build-tests -DCMAKE_BUILD_TYPE=Release
cmake --build build-tests --parallel
build-tests/motion_library_test --full
build-tests/mm_playback_dump --out motion_debug.csv
python3 tools/gen_motion_debug_video.py --csv motion_debug.csv --out motion_debug.mp4
```

The video encoder needs `ffmpeg` (or the optional `imageio-ffmpeg` Python package); alternatively specify `--format gif` with ImageMagick. It visualizes joint positions recorded from the production matcher on a **synthetic rig**, not rendered game footage. It first runs a scripted desired-motion route, then explicitly browses a brief sample of every loaded clip. The HUD's used count and clip-change count include this forced sweep, not just clips automatically selected during matching. It is not proof that every frame, retargeting on every character, or rendering on a phone is visually correct. The full-library test likewise checks a 12-frame browser sample per clip, finite outputs and category reachability, not complete visual playback.

LAFAN1 is by Ubisoft La Forge; review its license before distributing the motion data or derivatives. Generated CSV/video are intentionally not committed to the repository.

### Owner-controlled signing (preview only)

`android/build-apk.sh` defaults to an ephemeral debug key. To produce a consistently owner-signed **preview**, use an existing owner-controlled Android keystore and set `SAKUGA_ANDROID_SIGNING_MODE=owner`, `SAKUGA_ANDROID_KEYSTORE` (path), `SAKUGA_ANDROID_KEY_ALIAS`, `SAKUGA_ANDROID_STORE_PASSWORD` and `SAKUGA_ANDROID_KEY_PASSWORD` in the build environment before running the script. Password values are passed to `apksigner` via environment variable names, not command-line values. Do not commit the keystore or passwords, enable shell tracing, or upload them to a build log. Protect and back up the key: future updates must use the same signing identity (or follow the platform's supported key-rotation procedures). The output is named `Sakuga-Android-animation-preview-owner-signed.apk`; it is still only the experimental preview, not a production app. For Play distribution, additional Play App Signing, publishing, policy, privacy and device-validation work remains. CI tests the signing path with a disposable key that is never used for releases.

## On-device frame benchmark

In the Vulkan sandbox, tap **BENCH** on Android or click **Frame benchmark** in the Windows editor. Set up the scene first, start the test, and leave the camera and controls alone until it finishes. It warms up for 3 seconds, then samples at least 20 seconds of real wall-clock frame-loop intervals. The report records the Vulkan GPU, CPU when available, render resolution, starting scene, animation and key settings; on Android **Share report** opens the system share sheet, and on Windows **Copy report** copies the text. Send the report back here. Repeat under similar conditions (including power mode, temperature, scene and settings); this is a current-scene test, not a scripted flythrough. Changing settings or moving during the test makes comparisons unreliable. The test is cancelled on a render failure or a resolution change, and on Android when the app is backgrounded.

Average FPS is frames divided by measured seconds; p95 is the nearest-rank 95th percentile interval; 1% low FPS is the reciprocal of the average of the slowest 1% of intervals. The percentage over 16.67 ms uses a strict 1/60 second threshold and can include small timing jitter. These are CPU-side frame-loop intervals, not GPU timings or actual display scanout. FIFO presentation / vsync can cap the measured rate; a 60 FPS result does not prove performance on every scene. An emulator result is not a physical-device result. The Canvas fallback is a synthetic-rig preview, not the Vulkan 3D renderer, and does **not** provide this benchmark.

## Mixamo characters

Adobe requires a Mixamo account to download characters, and its FAQ restricts distribution of raw Mixamo character and animation files in engine/asset packages. No Mixamo assets are included here. A useful starting choice is **X Bot**, a standard humanoid; download it yourself from Mixamo and provide the FBX for an import/retargeting evaluation. Never send account credentials. Sakuga currently loads glTF/GLB/VRM, not FBX; Mixamo character import and retargeting are not yet implemented or verified. Converting FBX to GLB alone does not automatically provide the VRM humanoid mapping required by the current motion-matching path. See [Adobe's Mixamo FAQ](https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html) and [licensing FAQ](https://community.adobe.com/questions-696/mixamo-faq-licensing-royalties-ownership-eula-and-tos-589400).

### Current sky controls and FBX inspection

The sandbox's **Time of day / sky** panel now includes four artistic *palette* choices (Celestial, Cinematic, Atmospheric and Painterly) and cloud wind speed. These change colours on the existing procedural sky; they are not the standalone AnimeSky renderer, Hillaire atmosphere LUTs, 2.5D/volumetric cloud systems, weather transitions or GPU timestamp profiler described in the proposed roadmap. The existing Vulkan renderer and Android requirements remain unchanged.

The Windows package includes `sakuga-fbx-info.exe`, an offline diagnostic based on vendored ufbx. Run `sakuga-fbx-info.exe "C:\path\to\Jody.fbx"` in Command Prompt to inspect counts and bone names. It parses FBX but **does not import, animate or render it**; the sandbox still accepts glTF/GLB/VRM, not FBX. Jody was not available for testing or bundled, and Adobe's Mixamo restrictions still apply. A user-supplied Jody file is needed to develop and validate a real FBX rendering/retargeting path.

## Automatic starting quality and resolution

Windowed Vulkan chooses a **startup** quality tier from the Vulkan device type, not from a benchmark: Android, integrated, CPU and virtual devices start at **Performance** (75% internal resolution, 1× MSAA, bloom/point shadows/integrated sky off); discrete desktop GPUs start at **High** (100%, up to 4× MSAA); unknown desktop devices start at **Balanced** (85%, up to 2× MSAA). Actual MSAA is capped to supported counts. Saved sky profiles and later manual edits remain authoritative. All 77 motion clips remain available; the policy does not remove them. These are conservative heuristics, not promises of a frame rate or measurements of an Intel UHD or TECNO phone. Vulkan capability requirements and Android's Canvas fallback remain unchanged.

The internal HDR scene, post-processing and UI render at the chosen scale and are upscaled to the full presentation surface; this lowers pixel work and attachment memory but also softens UI and screenshots. Input remains in native surface coordinates. Scaling uses linear blitting where supported, otherwise nearest. At runtime, change **Render scale** in **Device and performance** or in Android **POST → Performance / resolution** (50–100%); resizing/rebuilding buffers can briefly stall and cancel a running benchmark. The override is retained through Android surface recreation, not app restarts. Bloom, shadows and sky controls remain independently editable. MSAA is selected at startup; to select a different tier on desktop launch with `--quality auto|performance|balanced|high`. `--render-scale 0.5..1` overrides the startup scale. The existing `--performance` launcher is still available. Headless captures keep the explicit requested dimensions. Adaptive resolution is enabled by default: it observes 5-second windows of wall-clock frame-loop intervals and, after three slow windows averaging over 40 ms, lowers scale by 0.05 to a minimum of 0.5. Four fast windows averaging under 25 ms raise it by 0.05, up to the startup/manual ceiling. Intermediate results reset the consecutive-window counts. Long gaps and benchmark sessions reset the sample history; adaptation is also suspended for command-line screenshot/recording. This heuristic cannot distinguish CPU bottlenecks, GPU bottlenecks, vsync, thermal changes or other interruptions, and rebuilding targets can briefly stall; it does not guarantee a target FPS. Disable **Adaptive resolution** in the same panel; moving the scale slider also disables it. When re-enabled, the current scale becomes the ceiling. Desktop options `--adaptive-resolution` and `--no-adaptive-resolution` override it, while `--render-scale` switches it off unless followed by `--adaptive-resolution`. Neither toggle nor scale is persisted across app restarts. At 1× MSAA the renderer avoids creating a redundant full-resolution HDR multisample colour image.
