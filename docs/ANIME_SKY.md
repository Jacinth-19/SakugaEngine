# Procedural sky: current implementation

The Vulkan sky draws four artistic palette styles, a sun/moon, stars and clouds. Each style now has an independently editable slot: scattering strength, Rayleigh/Mie artistic weights, cloud cover, wind, zenith/horizon tint, scattering/cloud mode and atmospheric model parameters. **Save sky profiles** writes all four slots; **Reset profile** resets the selected one. Profile choice itself and time of day are not saved in that file. A corrupt or incompatible file is rejected without changing the in-memory slots. On Windows the file is `%LOCALAPPDATA%/SakugaEngine/sky_profiles.json` when available; on Linux it is `$XDG_CONFIG_HOME/sakuga/sky_profiles.json` or `~/.config/sakuga/sky_profiles.json`; on Android it is the app's `<asset-root>/user/sky_profiles.json`. Fallback paths and save errors are shown in the editor/log. Android also retains unsaved changes during in-process surface recreation, not necessarily after process termination. The `SKY` button opens compact controls including scattering and a collapsible atmosphere model; colour tints are in the full editor.

## Atmosphere

`engine/sky/AtmosphereLut.h` computes a 256×64 linear RGBA8 transmittance LUT on the CPU. RGB contains Rayleigh, Mie and ozone extinction; alpha contains Mie-only transmittance. It integrates 48 midpoint steps in kilometres through a spherical planet with exponential Rayleigh/Mie densities and a triangular ozone layer. The x axis runs from the altitude-dependent geometric horizon to zenith, with a quadratic mapping that concentrates samples near the horizon; ground-occluded rays are rejected. RGBA channels store square-root-encoded transmittance and the shader squares the filtered values, providing more precision for dark transmittance than linear RGBA8. Height is the y axis. Radius, atmosphere height, Rayleigh/Mie scale heights, ozone strength and ground albedo are editable per profile (scattering coefficients and ozone-layer shape remain fixed). Inputs are clamped before use. A model edit rebuilds and uploads the LUT synchronously; in-flight GPU use is waited for and the old image freed. This can cause noticeable stalls while dragging sliders and has not been profiled on target hardware. Albedo does not require LUT regeneration.

The **Integrated scattering** option evaluates eight view-ray samples in the sky shader. Each sample has local extinction and a LUT lookup for sunlight at that point, including geometric ground occlusion. The observer altitude comes from world camera Y in metres, clamped to the atmospheric range; the planet is centred below the world origin. A simple isotropic ground-bounce term adds approximate reflected sunlight. The sun disc and optional volume clouds use atmospheric sun transmittance. A coarse CPU reference integration contributes to the procedural IBL when integrated scattering is on; sun, altitude and settings are quantised and the result is spatially interpolated for cost. This makes them more consistent, **not identical**: artistic gradient, cloud, sun and IBL treatments still differ. HDRI backgrounds bypass the sky shader. The optional depth-atmosphere post pass offers either artistic fog or a bounded single-scattering aerial mode using the sky LUT and model for opaque scene depths; see [post-processing details](POST_PROCESSING.md).

The unchecked integrated-scattering option uses the previous lower-cost LUT-informed artistic approximation. Strength zero disables the added sky scattering and returns to the original, unattenuated artistic sun disc; the LUT remains allocated. Integrated scattering defaults on for desktop, but off for Android unless a saved profile enables it. Rayleigh/Mie *artistic weights* scale in-scattering; they do not change extinction coefficients. The LUT is still eight-bit and horizon-to-zenith interpolation across altitude rows is approximate; filtering in the encoded domain is also approximate. Banding, near-horizon error and low-sun inaccuracies remain possible; no artist or real-device validation is claimed.

This is **not the complete Hillaire atmosphere**. There is no sky-view LUT, multiple-scattering LUT/solution, physically integrated ground bounce, or a complete physically based aerial-perspective solution. The optional post aerial mode handles only bounded single scattering through opaque depths. The single bounce is only an approximation, not a complete ground transport model. The sky is still combined with an artistic gradient and phase values are artist-scaled. Artistic fog, cloud shadows and transparent objects are not consistently lit by this model.

## Clouds

The default is the existing stylised 2D cloud shader. The opt-in **3D clouds (costly)** mode marches eight samples of procedural 3D density through a flat layer from 1.5 to 3.5 km, limited to 40 km, with wind and simple transmittance compositing. It is a basic real 3D density raymarch, not a production volumetric cloud system: there are no cloud shadow maps on scene objects, multiple scattering, temporal reprojection, weather map, adaptive quality, or physically integrated light paths inside clouds. It is drawn only in the background sky and does not create scene-depth intersections. Mobile defaults to the existing low-cost mode. Neither mode has been visually calibrated or benchmarked on the target devices.

## Profiling and verification

On queues supporting timestamps, the editor reports a delayed GPU **sky draw** sample separately from the post-processing sample. Queries are reset in the submitted command buffer and read after the frame's fence. This is not an atmosphere/cloud breakdown: scheduling and timestamp overhead can affect it, and tile-based GPUs may defer work. It is not a frame benchmark. Compare modes at fixed resolution, time, cloud cover and camera; validate on the actual Intel UHD and Android phone rather than using emulator timing.

GPU-free tests cover optical depth, ground intersections, model sanitisation, sampled single scattering, ozone/bounce response, profile round trips and malformed profiles. Android emulator smoke exercises the renderer and controls but does not establish visual quality, physical accuracy or physical-device performance. This is an incremental implementation, not finished AnimeSky 1.0.
